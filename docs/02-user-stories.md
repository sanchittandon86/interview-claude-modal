# 2. User Stories

## Generate

Translated the five business-problem functionalities into 9 user stories across three roles.

### Role: Seller

**US-1: Add New Product**
As a seller, I want to add a new product to my inventory, so that buyers can discover and view it in search.

*Acceptance Criteria:*
- Seller can submit a new product with its details and stock quantity.
- The new product becomes available for search/discovery once saved.
- Submission fails with a clear error if required product details or stock quantity are missing.

**US-2: Update Existing Product**
As a seller, I want to update an existing product's details or stock, so that the catalog reflects accurate, current information.

*Acceptance Criteria:*
- Seller can modify details and/or stock quantity of a product they previously added.
- Updated information is reflected in subsequent searches/views of that product.
- Update fails with a clear error if the product does not exist.

### Role: Buyer

**US-3: Search Products by Query** — Buyer can enter a search query and receive matching products; no matches returns an empty set, not an error.

**US-4: Filter Search Results** — Buyer can apply one or more filters (AND semantics); removing a filter re-expands results.

**US-5: View Ranked Search Results** — Results are ordered by relevance; ranking is consistent for repeated identical queries under unchanged inventory/filters.

**US-6: Navigate via Facets** — Buyer is shown facet options relevant to the current context; selecting a facet value updates results and applied filters.

**US-7: View Personalized Recommendations** — Buyer sees recommendations generated by the recommendation/ML system for their account/session; the platform displays them without altering the ML system's output.

### Role: Platform (System-level capture & handoff)

**US-8: Capture User Interaction Events**
As the platform, I want to capture buyer actions (searches, clicks, product views, scrolling, time spent, add-to-cart), so that this behavioral data can be used to generate recommendations.

*Acceptance Criteria (post-refinement, one line per event type):*
- A search event is logged when a buyer performs a search query.
- A click event is logged when a buyer clicks on a product or search result.
- A product view event is logged when a buyer views a product's detail page.
- A scroll event is logged when a buyer scrolls through a page/results list.
- A time-spent event is logged capturing the duration a buyer spends on a page/product.
- An add-to-cart event is logged when a buyer adds a product to their cart.
- Each logged event is structured and associated with the relevant product/session/user context.

**US-9: Store and Provide Events to Recommendation System**
As the platform, I want to persist captured events and make them available to the recommendation/ML system, so that personalized recommendations can be generated from real user behavior.

*Acceptance Criteria:*
- Captured events are persisted in storage.
- Stored events can be retrieved/provided by the recommendation/ML system (the system itself remains out of scope).

## Validate: Analysis & Discussion

| Metric | Result | Analysis & Discussion |
|---|---|---|
| Coverage | Pass | All five business-problem functionalities mapped to at least one story: inventory → US-1/US-2; search/filter/rank/facets → US-3–US-6; recommendation display → US-7; event capture → US-8; storage/handoff → US-9. No functionality fell outside the five defined areas. |
| Clarity & Specificity | Partial → Pass (after refinement) | US-8 originally bundled six distinct event types into a single grouped acceptance criterion, making it impossible to verify or test one event type failing in isolation. |
| Relevance | Pass | Every story traces directly to a target outcome in the business problem. No story introduced functionality beyond what was specified (no checkout, payments, reviews). |

### Refinement applied

US-8's single combined criterion was split into six explicit per-event-type lines (shown above), restating the same six event types at finer grain — no new functionality was added, only finer specificity. Re-validated as Pass on Clarity & Specificity.

## Outcome

9 finalized user stories, each with concrete, testable acceptance criteria, became the direct input to test-case design in Phase 3. Every later implementation decision was traceable back to one of these 9 stories by ID (US-1 through US-9).
